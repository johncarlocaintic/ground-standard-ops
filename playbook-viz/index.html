CloseBot Playbook · New Gym End-to-End

From intake to production. Five stages, three skills, one reference KDL. Vacaville Grappling Academy is the worked example in the right column of each stage so the diagram doubles as a concrete reference.

00 Pre-flight (Walking Skeleton) gate before /closebot-plan

Four cheap checks that catch the failure modes that ate Vacaville's Day 1. Block intake if any fail; do not paper over a missing prerequisite.

Checks (all must pass before /closebot-plan starts)
  1. GHL source attached. Confirm the gym has a CloseBot source (src_*) in GHL and that it appears in GET /agency/source. If absent, ask client to install CloseBot in their GHL location first.
  2. Knowledge-base material ready. At minimum: business hours, class schedule (with calendar names), trial offer language, prohibited topics (pricing, rival gyms). KB is attached to the source separately, not inside the KDL.
  3. Calendars exist in GHL with their final names. Get the exact calendar names (case-sensitive, spaces matter) via GET /agency/source/{sourceId}/calendars. The bot's Booking nodes reference these by name. Renaming after deploy means re-importing.
  4. CloseBot API key + GHL PIT verified. CloseBot: X-CB-KEY in client .env. GHL: PIT scoped to the location, header Version: 2021-07-28. Confirm both with one cheap GET each.
Block
If any check fails, stop. Do not start /closebot-plan. Surface what's missing to Idriss before doing anything else. Vacaville lost ~4 hrs on Day 1 by skipping this.

01 Plan /closebot-plan

Structured intake conversation. Idriss provides the gym's facts; Claude produces a spec JSON + a human-readable markdown spec. No KDL touched yet.

Inputs
  • Pre-flight checks have passed (Stage 00).
  • Gym facts from intake form, website, class schedule, KB source material.
  • Idriss available to answer clarifying questions in chat.
What Claude does
  1. Section 1 · Gym basics. Full gym name. Website URL. Brand voice notes.
  2. Section 2 · GHL setup. Location ID. CloseBot source ID. Confirm both resolvable via the agency endpoints.
  3. Section 3 · Calendars. Adult calendar(s) — exact GHL name(s). Youth calendars — for each: label, exact GHL name, age range (min/max). Variable cardinality: 0 to N youth bands.
  4. Section 4 · Programs. Which programs are bookable through the bot. Which are not (mentioned but redirect to front desk). Hard rule: no pricing pre-booking.
  5. Section 5 · Mission sentence + gym-specific rules. One- to two-sentence framing for the bot's conversationReason. Plus any hard restrictions for this gym (e.g. "do not mention wrestling"). Empty string if none.
  6. Section 6 · Flow shape confirmation. Confirm universals: adult path youth path multi-enrollee parent+youth combo minor gate. Note: these are always present; variance is only in the youth band count and age ranges.
  7. Section 7 · KB readiness. Confirm KB material is structured for upload (facts only, no instructional language, no pricing, no booking flow narration).
  8. Section 8 · Output. Write spec.json to clients/{slug}/closebot/{gym}/spec.json. Write human-readable spec.md alongside.
Decision gates
Persona lock
Persona is always "Emma". Do not ask. memory: feedback_persona_is_global.md
Spec completeness
Every Section field must be filled before producing spec.json. Empty values that should be intentional (e.g. gymSpecificRules can be "") must be explicit, not omitted.
Outputs
  • clients/{slug}/closebot/{gym}/spec.json — structured, consumed by Stage 02.
  • clients/{slug}/closebot/{gym}/spec.md — human-readable, for Idriss review before Stage 02 starts.

02 Build (Adapt + Deploy) /closebot-build

Claude reads the spec + the Vacaville reference KDL and adapts (not substitutes) the KDL for the target gym, then calls the CloseBot API to import, publish, and attach. Adaptation is by judgment because variance includes cardinality.

Inputs
  • clients/{slug}/closebot/{gym}/spec.json from Stage 01.
  • shared/sops/closebot-bot-build/vacaville-bot-template.kdl — the reference implementation. not a substitution template
  • Tier 2/3 docs: references/closebot_architecture.md, references/closebot_docs_reference.md, references/closebot_agent_node.md.
  • Client API keys from clients/{slug}/.env.
What Claude does (Phase 2 of /closebot-build SKILL.md)
  1. Read the reference KDL in full. Vacaville-shipped, ~2391 lines. Understand the universal flow before touching anything.
  2. Identify universal vs. variant against this gym's spec. Universal (do not restructure): adult Booking flow, youth Booking flow (1+), multi-enrollee path, parent+youth combo, minor gate (14-17 self-bookers diverted), Emma persona, NEPQ routing, scenarios, tag patterns, prohibited words, conversationReason / businessInformation shape. Variant per gym: youth calendar count, age-band labels, program names, calendar names, gymSpecificRules.
  3. Direct substitutions (find/replace exact, no paraphrasing). 
    # Config block
[GYM_NAME]              → spec.gym.name
[GYM_WEBSITE]           → spec.gym.website
[GYM_SPECIFIC_RULES]    → spec.gym.gymSpecificRules  # verbatim, "" if empty
[CALENDAR_ADULT]        → spec.calendars.adult

# Vacaville-shaped youth (substitute only if spec matches)
[CALENDAR_KIDS_3_5]     → spec.calendars.kids[label=kids_3_5].calendarName
[CALENDAR_KIDS_7_13]    → spec.calendars.kids[label=kids_7_13].calendarName
[CALENDAR_KIDS_10_14]   → spec.calendars.kids[label=kids_10_14].calendarName

# Wholesale replace these field values
conversationReason   ← spec.gym.conversationReason   # verbatim
businessInformation  ← spec.gym.businessInformation  # verbatim
  4. Adapt youth structure if non-Vacaville shape. Fewer bands: remove unused Booking nodes plus every descendant whose ID starts with the removed root's ID, plus all routing references (AISwitch cases, inbound handle="...", Next handle="...", True handle="..."). Tree-structured IDs make this surgical. More bands: clone an existing youth Booking node, generate a new unique id="...", add a matching AISwitch case, wire Next handle= back to the shared downstream path. Different age ranges (same count): rewrite each AISwitch CaseName "..." to match the gym's bands; keep IDs as-is.
  5. Scenario + tag substitutions. Replace ScenarioCustom blocks with spec.scenarios. Update TagsToAdd blocks with spec.tags values.
  6. Orphan-handle validator. Grep every handle="X" in the adapted KDL; confirm X exists as an id="X" elsewhere in the file, or is the literal sentinel EOC (CloseBot's end-of-conversation handle). Any unmatched handle = silent broken routing.
  7. Strip duplicate __zIndex entries. CloseBot importer 500s on duplicate __zIndex within a block. Dedupe per-block before POST /bot. memory: feedback_closebot_kdl_dedupe_zindex.md
  8. Archive previous version (iteration safety). If a bot is already attached to the source, detach it first, rename to LEGACY · {original name} · YYYY-MM-DD, move to a "Deactivated" folder in the CloseBot UI. memory: feedback_iteration_source_detach.md + feedback_legacy_deactivation.md
  9. Import the adapted KDL. 
    POST https://api.closebot.com/bot
Headers: X-CB-KEY: $CB_KEY
Body: { name: "{Gym} Launch v1.0 [initial build] (YYYY-MM-DD)", importKdl: "..." }
→ { bot: { id: "bot_XXXXX" } }
  10. Publish. 
    POST https://api.closebot.com/bot/{botId}/publish
Body: {}
  11. Attach to GHL source. 
    POST https://api.closebot.com/agency/source/{sourceId}/attach
Body: { botId }
    Use the production source (e.g. src_GDKORXSW4Q8RQUQ8) or the GS Ads sandbox source (src_4R4DUIQTMMX2NFPU) depending on whether this is a real deploy or a sandboxed eval setup.
  12. Read back the published bot config. Critical: deploy strips prohibitedWords values silently. Read back via GET /bot/{botId} and restore via PATCH if stripped. memory: feedback_closebot_prohibitedwords_stripped_on_deploy.md
Decision gates
Block import if orphan handles exist
No exceptions. A broken handle import looks clean but routes users into dead-end paths. This is the bug pattern that ate days on Vacaville and forced the 2026-05-11 playbook reset.
5 ScenarioCustom max
Exceeding fails publish with "Too many custom scenarios attached to bot." If the spec needs more, consolidate before this stage.
Use bot UI names, not IDs (in chat)
When reporting status to Idriss, reference bots by their visible name in CloseBot UI, never by bot_XXXX IDs unless explicitly asked. memory: feedback_use_bot_names_not_ids.md
Outputs
  • Adapted KDL written to clients/{slug}/closebot/{gym}/{version}.kdl (for git history).
  • Bot live in CloseBot (bot_* id), published, attached to its assigned source.
  • Previous version (if any) detached, renamed LEGACY, moved to Deactivated folder.
  • Deploy record written to clients/{slug}/closebot/{gym}/deploy-log.md with bot id, source id, timestamp.

03 Test (Pre-launch QA) /closebot-test

Eval orchestrator runs the bot against a gym-specific rubric and persona set. Four agents per persona: Tester (simulates user) → QA Agent (transcript-vs-rubric) → GHL Verifier (real GHL facts) → Judge (final verdict). Aggregate pass-rate determines launch readiness.

Inputs
  • Deployed bot attached to the eval sandbox source (src_4R4DUIQTMMX2NFPU for GS, never the production source memory: project_vacaville_test_source_routing.md).
  • Gym-specific rubric (rubric.json) defining pass criteria per persona type.
  • Persona set (8 typical adversarial cases): adult inbound, parent enrolling kid, minor self-booker, multi-kid parent, ages-bracket-edge, off-topic-prober, KB-gap-tester, booking-changer.
  • Eval orchestrator scripts in shared/scripts/closebot/eval/.
What the orchestrator does (per persona, repeated 8x)
  1. Tester (simulated user). Opens a CloseBot SSE test session against the bot with mimicSourceId set to the sandbox source. Sends messages following the persona script. Captures the full transcript including SSE event log (which nodes fired, which tags were applied, which scenarios matched). 
    POST /bot/{botId}/testSession
Body: { mimicSourceId: "src_4R4DUIQTMMX2NFPU" }
# Then exchange messages via the SSE stream
  2. Test identity randomization. Every run randomizes lastname, email, phone (firstname stays "Tester"). Prevents GHL contact collision across runs. memory: feedback_test_identity_randomization.md
  3. QA Agent (rubric check). Reads the transcript + the rubric. Verdicts: did the bot follow flow? Did it avoid pricing pre-booking? Did it apply NEPQ correctly? Did it route to the right calendar?
  4. GHL Verifier (real-world facts). Queries GHL API: was the contact created? Were the right tags applied? Were the right custom fields populated? Was an appointment booked under the right calendar? Cross-references against the rubric.
  5. Judge Agent (final verdict). Reads QA Agent + GHL Verifier outputs. Produces pass/fail per criterion + overall verdict per persona. Writes judge_assessment.json.
  6. Cross-examine judge output. Idriss never accepts the Judge verdict at face value. Always cross-reference ghl_facts.json + SSE event log + GHL API directly before treating a verdict as ground truth. memory: feedback_cross_examine_judge_output.md + feedback_closebot_logs_standard.md
  7. Aggregate. Roll up per-persona verdicts into a single pass-rate (X/N). Produce a markdown report with verdicts, failure categorizations, and clickable links to every transcript log. memory: feedback_link_transcripts.md
Decision gates
Hard guardrail: source routing
Never use the production source as mimicSourceId in evals. Bookings created during evals fire into real GHL calendars and pollute client data. Sandbox source only.
Launch readiness threshold
Idriss decides per gym. Typical: ≥80% pass with no P0 failures (e.g. wrong calendar booked, pricing mentioned pre-booking, minor not gated).
Attach/detach protocol
Attach bot to sandbox source before the eval starts. Detach after. One bot attached per source at a time. memory: feedback_test_attach_detach_protocol.md
Outputs
  • Per-run artifact folder: shared/scripts/closebot/eval/runs/{gym}/{YYYY-MM-DD-HHmm}/
  • transcripts/{persona}.log — full SSE conversations.
  • ghl_facts.json — what actually got created in GHL.
  • judge_assessment.json — final verdicts per persona.
  • summary.md — aggregate pass-rate + clickable links to every transcript.

04 GHL Wiring (Trigger + Filters) GHL UI · per-client workflow

Move the bot from sandbox to production source. Wire the GHL workflow that fires the bot on the right contact event. Lock down the kill-switch.

Inputs
  • Bot passed Stage 03 with acceptable pass-rate.
  • GHL location admin access.
  • Production source ID (src_*) for the gym's GHL location.
What gets configured (in this order)
  1. Detach bot from sandbox, attach to production source. If a legacy bot is still attached to production, detach + rename + move to Deactivated first. One bot per source at a time.
  2. Source filters (universal across all gyms). Must Contain: the bot-specific trigger tag (e.g. lead replied - enquiry & storm lead responder). Does Not Contain: ai off — universal kill switch.
  3. GHL workflow trigger. Match the trigger pattern to the campaign type. Most common: Contact Tag Added with the gym's trigger tag. Date-based campaigns: Date/Time trigger + custom date field + offset. External events (rare): n8n webhook relay → applies tag → workflow fires.
  4. Conversation routing. The workflow's "Send to CloseBot" step references the attached source. No bot ID is hardcoded — CloseBot resolves the active bot from the source at runtime.
  5. Test the live trigger end-to-end with a sandbox contact. Create a test contact in GHL with the trigger tag. Confirm the workflow fires, the bot picks up, the conversation proceeds, the appointment writes back to the right calendar.
Decision gates
Kill switch verified
Apply ai off tag to the test contact. Confirm the bot stops responding. This is the universal escape hatch when behavior goes sideways in production.
Old version archived, not deleted
Never delete legacy bots/workflows. Deactivate + move to "Deactivated" folder across CloseBot, GHL, n8n, Retell. memory: feedback_legacy_deactivation.md
Outputs
  • Bot live on production source.
  • GHL workflow active, trigger tag verified firing.
  • Kill switch (ai off) confirmed effective.
  • Legacy bot detached + renamed + archived (if applicable).

05 Production live · monitor · iterate

Bot is live and handling real leads. The work shifts from build to observe: cross-reference logs, verify GHL appointments, respond to flagged conversations, iterate.

Inputs (real-time)
  • Real leads arriving via Meta Ads / web forms / referrals → land in GHL with the trigger tag → workflow fires → bot conversation starts.
  • Client feedback (Bobby, Kevin, etc.) via WhatsApp / Slack / EOD threads.
What we monitor + respond to
  1. Daily check on flagged conversations. CloseBot logs show every conversation. Filter for: concierge - failed booking tag, contacts that dropped mid-flow, contacts where ai off was applied (client escalation).
  2. Cross-reference CloseBot logs with GHL appointments. A "successful booking" in CloseBot must produce an appointment in the right GHL calendar. Mismatch = silent failure. Run periodic spot-checks. memory: feedback_closebot_logs_standard.md
  3. Client EOD reports. Per-client EOD logged to clients/{slug}/eod-reports/ + time-log.md. For NewWine clients (Bobby/Kevin/Lehman), signed as JC. For BBC (Melissa), signed as Idriss. memory: feedback_eod_persona_rule.md + feedback_eod_log_for_compensation.md
  4. Iteration trigger. Client feedback or observed failure pattern in production → spec update or KDL adaptation needed → restart from Stage 01 (Plan) or Stage 02 (Build), keeping the trigger tag stable. memory: feedback_iteration_source_detach.md
Decision gates
Production source guardrail
No evals against the production source. No "just one quick test." If you need to test, use the sandbox source.
Retry before declaring failure
CloseBot/GHL APIs can have transient errors. Retry 2-3 times before reporting a failure conclusion. memory: feedback_retry_before_conclude.md
Verify before diagnosing
Never build a narrative from a single error string. Query the underlying system (GHL /calendars, /export, CloseBot logs) before claiming a cause. memory: feedback_verify_before_diagnosing.md
Outputs (ongoing)
  • Booked appointments arriving in GHL calendars → client closes sales.
  • EOD reports stacked in clients/{slug}/eod-reports/.
  • Iteration tickets in tasks/todo.md when failure patterns emerge.
  • Memory entries when the same failure pattern surfaces 3+ times → graduates to a CLAUDE.md rule or a skill.
